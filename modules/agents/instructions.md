# コーディング方針

プロジェクトの規約（そのプロジェクトの AGENTS.md、CONTRIBUTING、lint やフォーマッタの設定など）と衝突する場合は、常にプロジェクト側に従う。

## 原則

- コードは実現したい動作のために書く。動作に寄与しないコードを足さない。
- 数ヶ月後の自分を含む他人が、最短で理解できることを優先する。そのためなら記述が多少冗長になってもよい。

## コメント

書く:
- 処理の意図
- 一般的でない実装を選んだ場合、その理由
- コード外部の情報への参照（issue 番号、論文、ハードウェア仕様など）
- 数行のまとまりの要約（ただし先に関数への切り出しを検討する）

書かない:
- コードを読めば容易に分かること（`i++ // i を増やす` など）
- 変更履歴（「〜を追加」「〜に変更」「〜を修正」など）。これは git の役割
- ログと重複する内容、ログで出力すべき内容
- 変数名・関数名で表現できること

## 関数化

- 要約コメントを書きたくなったら、まず関数への切り出しを検討する。
- 切り出す目安: 一言で命名できる（`and` が要るなら分割する）、引数と戻り値が少なく書ける、単体でテストする価値がある。
- 切り出さない目安: 周囲と状態を密に共有している、切り出すと読み手が定義を行き来する回数が増える。この場合は要約コメントで残す。

## 命名

- 名前から役割や計算コストを誤解されないようにする。`get` や `size` は軽い処理にだけ使い、通信やダウンロードを伴うなら `fetch` `download` のように具体的な動詞を選ぶ。
- 結果の向きが曖昧な語を避ける（`filter` ではなく `select` / `exclude`）。
- 値の解釈に必要な前提は接頭辞・接尾辞で名前に含める（単位: `timeout_ms`、座標系: `pose_in_base`、可否: `can_` など）。
- 関数名は基本的に動詞＋名詞。必要なら前置詞や副詞で曖昧さをなくす。
- `tmp` や `i` のような汎用的な名前は、スコープが狭い場合に限る。
- private な関数、メンバ変数などの命名規則は、言語の慣習に従う。

## 構造

- 整形はフォーマッタに任せ、手で縦揃えなどをしない。
- 関連する宣言・処理は近くにまとめて配置する。
