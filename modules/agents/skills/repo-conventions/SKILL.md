# リポジトリの作り方

## 目的

リポジトリの外から来た人（数ヶ月後の自分、他の開発者、コーディングエージェント）が、迷わず使い始められ、設計意図を把握でき、作業の続きを拾えるようにする。
そのために、ドキュメントごとに役割を分け、同じ情報を複数の場所に書かない。

## ドキュメントの役割分担

| ファイル | 書くこと | 書かないこと | 更新するとき |
| --- | --- | --- | --- |
| `README.md` | クイックスタート（何をするものか、入れ方、最小の使い方） | 設計の説明、内部構造 | 使い方が変わったとき |
| `DESIGN.md` | 実装している内容の簡易仕様と、設計意図（なぜその構造・方式を選んだか） | 作業の予定、コードを読めば分かる細部 | 設計を変えたとき。変える前に読む |
| `TODO.md` | ユーザーとエージェントがやるべき作業の管理 | 終わった作業の履歴（git の役割） | 作業を始めるとき・終えたとき |
| `AGENTS.md` | コードや manifest を読んでも分からない、このリポジトリ固有の事実とルール | ディレクトリ構成、コードスタイル、全リポジトリ共通の方針 | ルールや環境が変わったとき |

同じ情報が必要になったら、コピーせず他のファイルへの参照を書く。コピーはどちらかが古くなる。

## AGENTS.md

判断基準: 「コード・manifest・他のドキュメントを読んでも分からない」かつ「間違えたときのコストが高い」ものだけを書く。
AGENTS.md は作業のたびに読み込まれるので、不要な行はすべての作業の焦点を薄める。

書く:
- 非自明なツールの選択（例: Python の依存管理は uv。pip は使わない）
- 完了の定義（何のコマンドが通れば変更が完了か）
- 触ってはいけないもの（生成物、vendor されたコード、ツールが自動更新するファイル）
- 環境依存の罠（特定のマシン・OS でしか動かない処理など）
- 全リポジトリ共通の方針（グローバルの指示）からの例外
- 他のドキュメントへの参照（例: 設計を変える前に DESIGN.md を読む）

書かない:
- ディレクトリ構成の一覧。エージェントは自分で読める。更新の手間がかかり、古くなる
- コードスタイル。フォーマッタと linter に任せる
- 特定の作業でしか使わない手順。別ファイルに分け、AGENTS.md には参照だけを書く
- コード片のコピー。`path:line` で参照する

テンプレート: `templates/AGENTS.md.tmpl`

## DESIGN.md

他の人が設計意図を把握できることを目指す。「何をしているか」より「なぜそうしているか」を優先する。
採用しなかった案があれば、その理由も残す。後から同じ検討を繰り返さないため。

テンプレート: `templates/DESIGN.md.tmpl`

## TODO.md

エージェントへの要求（毎回言わなくても守ること）:
- 会話中に TODO.md を参照し、作業の開始・完了に合わせて更新する
- コマンドで表せる作業は、手順を書く代わりにスクリプトとして用意する
- 項目の粒度を揃える（1項目 = 1回の作業で終わる大きさ）
- 類似した項目はまとめる

テンプレート: `templates/TODO.md.tmpl`

## 手順

### 新しくリポジトリを作るとき

1. 目的と使う言語をユーザーに確認する
2. 言語のエコシステムの標準的な方法で初期化する（`cargo new`、`uv init` など）
3. `templates/` から必要なファイルをコピーし、拡張子 `.tmpl` を外して埋める
4. 埋める内容がないセクションは消す。空の見出しを残さない

### 既存のリポジトリを見直すとき

1. 各ドキュメントを読み、上の役割分担と照らし合わせる
2. 役割から外れた記述、重複、古くなった記述を挙げる
3. 書き換える前に、変更案をユーザーに見せて確認する

## 未決事項

以下はまだ方針が決まっていない。エージェントはここを規約として扱わず、判断が必要になったらユーザーに確認する。

- フォルダ構成の基本形。言語ごとの標準レイアウトに従う前提で、その上に足すもの（`docs/`、`scripts/` など）をどうするか
- git の慣習（コミットメッセージ、ブランチ名、リポジトリ名）
- コマンドの集約先（justfile などのタスクランナーを使うか）
- TODO.md をディレクトリに分けるか
